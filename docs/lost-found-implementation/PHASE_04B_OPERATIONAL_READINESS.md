## 8. تصميم اختبارات تنافس MySQL الحقيقية

الحالة: **التصميم PASS؛ التنفيذ NOT TESTED**.

ستستخدم قاعدة مقترحة باسم `laraseed_phase04b_test` فقط، تُنشأ من schema نظيف أو من نسخة منقحة، واتصالين PDO مستقلين على MariaDB/InnoDB/REPEATABLE-READ. لا تستخدم قاعدة `laraseed`. ينسق runner عمليتين مستقلتين عبر pipes/رسائل `READY/COMMIT`؛ لا يعتمد على sleeps وحدها. كل سيناريو ينشئ fixtures مميزة، يأخذ snapshot، ثم ينظف قاعدة الاختبار كاملة بعد تسجيل النتيجة.

- **A — تحقق علاقتين متعارضتين:** يمسك العامل الأول قفل العنصر/البلاغ قبل التوثيق، ويبدأ الثاني توثيق نفس البلاغ مع عنصر آخر ثم العكس. بعد تحرير الحاجز يجب أن تلتزم علاقة واحدة فقط، ويرفض التطبيق/unique constraint الأخرى بلا سجل جزئي.
- **B — تسليمان متنافسان:** عمليتان تكملان التسليم لنفس العنصر والمطالبة. يجب أن يوجد Handover واحد وحدث `handed_over` واحد، وتصبح القطعة `returned` مرة واحدة؛ العملية الثانية ترى الحالة الحالية وتفشل.
- **C — مراجعة استجابة متعارضة:** عمليتان تبدآن من `submitted`؛ إحداهما review والأخرى cancel/reject. بعد قفل الصف لا يقبل إلا مسار قانوني واحد، ويطابق سجل التدقيق الحالة النهائية.
- **D — سباق العلاقة والتسليم:** تحجب عملية توثيق الرابط قبل commit بينما تبدأ عملية التسليم. لا يجوز للتسليم استخدام رابط غير committed؛ إما ينتظر ثم يكمل بالرابط الحالي الصحيح، أو يفشل بلا آثار نهائية.
- **E — الفشل والـ rollback:** يحقن استثناء بعد إنشاء الرابط وقبل سجل مراجعة الاستجابة في MySQL الحقيقي. يجب ألا يبقى link أو تحديث استجابة جزئي.
- **F — حماية البلاغات غير المرتبطة:** تنفذ الاستجابة والتسليم مع بلاغات active/draft أخرى وتُقارن snapshots؛ يتغير البلاغ المرتبط المؤهل فقط عند التسليم الفعلي، وتبقى البقية حرفياً كما كانت.

يسجل runner connection IDs، isolation، زمن الانتظار/نتيجة deadlock إن وجدت، الحالات النهائية، أعداد السجلات، وSQLSTATE المنقح بلا بيانات شخصية.
